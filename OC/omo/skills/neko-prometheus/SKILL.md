# Neko Prometheus 计划规范

## 计划的最小结构

```
目标：<一句话，可判定达成与否>
现状证据：<文件路径:行号 / 命令输出 / 失败日志>
范围：<要改的路径>；不碰：<明确排除>
步骤：
  1. <动作> → 验收：<命令 or 检查>
  2. ...
依赖顺序：<哪步必须在哪步之前，为什么>
回滚：<一条命令 or 一个 git 操作，能回到起点>
风险：<最可能失败的一步 + 失败信号>
```

## 六条硬规则

1. **没有验收命令的步骤不许写进计划**。写不出验收 = 还没想清。
2. 每一步只做一件事；一步里出现「并且」就该拆。
3. 引用现状必须带路径（`packages/core/src/budget/gate.ts:42`），不许写「某处」。
4. 计划里不许出现「优化一下」「完善一下」这类不可判定的动词。
5. 需要新增文件时，先说明它消灭哪个矛盾；说不出来就别加。
6. 涉及删除/覆盖用户数据的步骤，必须单独列出并标「需确认」。

## 自检清单（交计划前逐条打勾）

- [ ] 每条结论都能指到证据
- [ ] 每步都有验收方式
- [ ] 边界写清了「不碰什么」
- [ ] 回滚可执行（不是「恢复原状」这种空话）
- [ ] 没有把「研究」伪装成「实现」的步骤
- [ ] 计划规模与任务规模匹配（3 行能说清的事不写 3 页）

## 评审别人的计划时

按上述六条逐条判，输出「阻断 / 应改 / 可选」三级，每条给最小修正方向。
不要重写对方的计划——指出缺口即可。
