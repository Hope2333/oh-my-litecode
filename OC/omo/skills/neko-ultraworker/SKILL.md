# Neko Ultraworker 作业流程

## 1. 先判类型，再动手

| 类型 | 判据 | 动作 |
|---|---|---|
| 一次可完成 | 改动点 ≤ 2 个文件，无需设计判断 | 直接做，做完验证 |
| 可分解 | ≥ 2 个互不重叠的单元 | 切分 → 派发 → 验收 |
| 方向不明 | 缺关键证据或存在 2 倍以上工作量差的解读 | 先派 explore/librarian，或直接问用户一句 |

## 2. 切分单元的硬标准

- 每个单元**只有一个交付物**（一个文件、一个命令结果、一份结论）。
- 单元之间**路径不重叠**：两方都要改同一文件，就不是并行单元，是顺序步骤。
- 每个单元必须能独立验收；验收不了的单元说明切错了。

## 3. 派发 brief 的四要素（缺一即拒绝派发）

1. **目标**：要产出什么，一句话。
2. **产出**：具体文件路径 / 命令输出 / 结论格式。
3. **边界**：只许碰哪些路径；明确列出「不许碰」。
4. **验收**：跑什么命令算过；失败怎么办。

## 4. 验收（不可跳过）

子代理说完成不等于完成。逐条核：
- 文件真的存在？内容与 brief 一致？
- 验收命令真的跑过？把输出贴出来（没有输出视为没跑）。
- 有没有超出边界改动？（`git status` / `git diff --stat`）
- 有没有引入禁止模式（any / ts-ignore / 空 catch / 删测试）？

任一条不成立 → 带着具体缺口续接**同一个**子代理会话，不要新派。

## 5. 失败恢复

1. 第一次失败：指出具体错误，续接同一会话修。
2. 第二次失败：换角度——让子代理先复现问题并给根因，不许直接改。
3. 第三次失败：停手，回滚到可用状态，把三次尝试与证据交给人或 oracle 判断。

## 6. 你自己不下场实现的情况

- 需要跨 3 个以上文件的机械改动
- 需要长时间试错（bench、渲染、抓取）
- 需要独立视角复核（momus/oracle）

其余情况你自己做更快——派发是有成本的。
