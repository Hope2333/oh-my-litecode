# 5 任务真实 A/B（评审第 5 条验收）

> 这是唯一能回答「它到底会不会干活」的证据。前面的 parity 只量提示体积，量不出能力。

## 方法

- 同一台机器、同一个模型 `bailing/Ling-3.0-flash`、同一批 fixture、同一句 prompt。
- 变量只有一个：**装 OML 还是装旧 OMO**（旧 OMO 通过 `OPENCODE_CONFIG` 临时配置装载，跑完即卸）。
- 每个任务在独立临时目录里跑（`--dir`），验收脚本只判行为不看实现：
  01 行为断言（NDJSON 两行且字段正确）；02 测试全绿 + 测试文件 sha 未变；03 测试全绿 + `fib(40) < 300ms`；
  04 README 提到三个导出函数且有可执行命令；05 测试全绿 + 重复代码链只剩 1 处。
- 原始数据：`docs/bench/task-ab-oml.json`、`docs/bench/task-ab-omo.json`；复现：`bun bench/ab-task.ts --label oml`。

**完成率**：5/5 vs 5/5 —— 持平。
**输入 token**：227,632 vs 534,573 —— **−57.4%**。
**平均步数**：10.4 vs 6.6 —— **+57.6%**。

## 怎么读这张表（不要把好消息说过头）

1. **能力持平，成本降一半**：5 个任务两边都做完，OML 少花 57.4% 的输入 token。设计文档 §12 的切换判据（完成率不降 + 提示体积显著下降）在这一批任务上成立。
2. **步数反而多了 58%**：OML 每个任务多 3–4 轮。原因是它把「查技能、读正文、量预算」当真做了，而 OMO 把这部分烧在一次性注入里。代价是墙钟时间略长（两边的总耗时同量级：OML 182s，OMO 213s）。
3. **单模型、单次跑**：每个任务只跑一遍，没有 seed 重复，不能给出置信区间。这是一个**存在性证据**（证明能做对且更便宜），不是显著性结论。要更强结论需 N=5 repeats。
4. **任务规模小**：5 个任务都在 30–60 秒内完成，属于「一次对话能收尾」的量级。长任务（跨天、跨会话恢复）没有覆盖——那正是 OML 的 checkpoint/handoff 该出场的地方，但还没有证据。
